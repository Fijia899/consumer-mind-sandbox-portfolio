## 1. 产品目标与两个入口

产品定位：帮助旅游产品经理分析旅游方案如何满足用户需求，并通过对话探索方案取舍的消费者沙盘 Agent。

| 入口 | 用户输入 | 核心交付 |
| --- | --- | --- |
| 个性化分析 | 自主添加角色，上传聊天记录、电话录音或访谈资料，再选择角色填写旅游方案 | 自动画像草稿、可核查依据、逐项需求满足情况、缺口及方案修改建议 |
| 通用分析 | 填写旅游方案、目标旅游人群和业务约束，选择画像原型库 | 多画像覆盖矩阵、共性需求、冲突人群、方案取舍对照与迭代建议 |

两个入口共享 Agent 执行层、旅游 JTBD 维度、方案版本和分析工作区；画像与报告明确标记类型及适用范围。

研究对象始终为旅游意向人群。允许基于原始资料推断需求，但自动生成的推断必须独立标记，不能升级为人物事实。规则角色可作为通用分析中的画像原型保留，也可以供用户选择做情境推演；不能和真实来源角色混淆。

## 2. 角色体系

| 类型 | 来源 | 使用方式 |
| --- | --- | --- |
| 规则画像原型 | 预设旅游决策维度及明确的情境假设 | 通用分析与假设情境分析，不冒充真人 |
| 自定义原型 | 用户手动配置预算、同行、节奏等假设条件 | 加入个人原型库，独立标记为假设 |
| 资料角色 | 用户指定对象并提交聊天、录音、访谈等资料 | 个性化分析；自动画像草稿经核对后保存版本 |

“自主添加角色”同时提供“上传资料生成”和“手动创建原型”两个方式。用户没有原始资料时仍可建立原型；系统展示的是条件推演，不使用真人已核验等标签。

画像字段分为四类：明确自述、经用户补充确认的信息、AI 推断、未知。用户确认需记录确认者及依据；操作者的确认不自动等同于被分析对象本人的确认。编辑推断标签不能使其变成原文事实。

## 3. 个性化分析流程

1. **添加角色**：填写研究标签或匿名编号，声明分析对象、旅行情境及材料可用范围。
2. **提交资料**：首版支持粘贴文本、TXT、结构明确的 JSON，以及 MP3/M4A/WAV 电话录音。材料转录所需处理范围在提交前说明；文件大小和时长上限根据所选转录服务验证后配置。
3. **识别发言归属**：聊天记录区分客户、销售等发言者。电话录音先转录并提供时间戳，再让用户核对说话人与分析对象；不通过声音自动确认现实身份。
4. **自动生成画像草稿**：提取旅行目标、同行安排、预算约束、时间、决策因素、担忧、可妥协项和未知项。没有信息的年龄、职业、收入等保持未知。
5. **核对与保存**：画像卡能点击回到聊天片段或录音时间。用户可修改、排除错误归属、处理矛盾，保存为可选择的角色版本。自动生成不要求逐字段手工填写，但关键来源和发言归属需要核对。
6. **选择角色和情境，填写方案**：方案可直接粘贴自然语言，Agent 整理成行程、总价/费用范围、住宿、交通、退改、服务承诺等草稿供核对。
7. **检查需求满足情况**：逐项输出满足、部分满足、冲突、未覆盖或无法判断，并展示对应人物依据与方案片段。
8. **探讨与迭代**：用户可补充条件、调整优先级或修改方案；Agent 调用相关工具重新分析，生成版本差异，不改写历史报告。

报告表格示例结构：需求｜依据与归属｜方案承诺｜满足状态｜决定性约束｜待确认问题｜修改建议。

AI 可提出“更看重行程确定性”等解释，但必须标注为推断并引用依据。录音中销售人员描述的预算不能直接当作客户自述；未答复不等于同意，历史行程不等于当前出行计划。矛盾资料分别保留并要求澄清，不静默选择更有利的一条。

需求匹配与是否愿意进一步了解分别呈现。满足已知需求不等于必然愿意咨询、预订或付款；原三组意向预测及本人反馈流程作为独立验证能力保留。

## 4. 通用分析流程

1. 用户输入旅游方案，并限定目标范围，例如亲子周末游、独自短途游或多人结伴游；不知道时可由 Agent 提出候选范围供选择。
2. Agent 提取预算、天数、同行、节奏、交通、安全、无障碍需求、退改等决策维度，读取原型库并建立覆盖计划。
3. 按差异选择画像原型，展示选择原因、未覆盖维度及计划分析规模。首版可从 20–40 个有明显差异的“原型 × 旅行情境”案例起步；这是可配置实验规模，不是现有人数或人口样本。
4. 分批分析并去重，发现重大覆盖缺口或反例时扩充案例，直到达到用户预算或新增案例不再提供实质新问题。不能只挑容易满足的画像。
5. 展示每种原型的需求满足矩阵、共性问题、冲突与不可满足约束，不将同一原型的重复采样当成新增人群。
6. 用户与 Agent 讨论修改方向，生成 2–3 个候选版本，在同一冻结案例集和权重下对照；新增原型的扩展结果另外展示。

“尽可能多、多方面”落实为可解释的差异覆盖，而非无限增加模型生成的人物数量。首版保留原型来源、版本、约束及生成假设；对相互冲突或不可能同时成立的条件组合进行校验。跨批次固定案例 ID，失败案例留在总数中。

### 如何表达“满足大多数人”

没有代表性真实样本和可信权重时，页面使用“当前原型集合的需求覆盖”，说明覆盖的是哪些原型，不声称满足多数真实游客。

- 无权重时，每个不同原型只计一次；可以显示满足/部分满足/冲突/未知的数量和占比，但分母明确为本次原型集合。
- 对每个“原型 × 情境”预先定义关键需求和硬约束；只有全部适用硬约束与关键需求满足，才计为满足。部分满足、未知、未分析和失败分开统计。
- 如用户提供策略权重，显示其来源为用户假设，只作策略情景分析；真实样本权重需有抽样或业务数据依据及版本。
- 结果同时展示全部案例、已完成案例、未知及失败占比，不能移除难分析的案例后抬高覆盖率。
- 有真实样本及权重后，可报告该样本范围的加权结果与不确定性；推广到目标总体仍需检查抽样方式、偏差与代表性。增加 AI 原型数量不能替代此验证。

## 5. 方案取舍与对话优化

优化目标由用户确定。Agent 先识别不可违反的业务约束，例如售价上限、服务成本、行程天数和已确认资源；未提供成本数据时，不推算利润，不承诺“降价但利润不变”。

共同优化过程：

1. 找出影响多类原型的共性缺口，以及只影响特定原型的冲突。
2. 生成少量具体修改，说明依赖的资源与待验证条件。
3. 对每个候选方案使用相同案例集、需求判定标准与权重重新分析。
4. 展示哪些原型受益、哪些受损、哪些仍未知，以及预算/服务条件的变化。
5. 提供不同取舍方向供用户决定，例如成本优先、覆盖优先、保护特定需求；可提出基础套餐加可选项，而非强行让一个版本适合所有人。

目标是寻找当前集合与约束下更好的方案，不承诺全局最优或真实市场最大化。修改不得隐藏原型的已知安全、无障碍等硬约束；任何单一汇总指标旁保留分组明细。

示例仅为方案假设：增加夜间接站可能改善晚到达情境的覆盖，同时增加服务成本；应核实可用车辆和报价后再纳入正式承诺。

## 6. Agent 在两条链路中的职责

采用单 Agent 与受控工具，按中间结果选择下一步。个性化链路中选择解析、转录、归属核对、提取和追问；通用链路中选择原型、检查覆盖、发现反例和对比方案。原文校验、类型隔离、约束检查与权限控制由代码执行。

| 能力组 | 计划工具 | 关键边界 |
| --- | --- | --- |
| 资料处理 | `parse_chat`、`transcribe_audio`、`resolve_speakers` | 录音由转录服务处理；时间戳、说话人和原文版本可追溯 |
| 画像生成 | `extract_profile`、`validate_profile`、`save_profile_draft` | 推断与事实分开，生成只保存草稿；用户核对后生成可选择版本 |
| 角色读取 | `get_profile`、`get_episode`、`get_evidence` | 类型、人物、旅行情境和版本隔离 |
| 方案分析 | `parse_plan`、`analyze_needs`、`validate_claims` | 人物依据和方案承诺双向引用；缺失不补造 |
| 原型覆盖 | `select_archetypes`、`check_diversity`、`analyze_batch` | 服务端限制批次、并发和总案例数，拒绝重复凑数 |
| 迭代与交付 | `propose_changes`、`compare_versions`、`ask_user`、`submit_report` | 不改变对照分母与硬约束；报告可查看来源和运行事件 |

单次执行中的工具数、模型 token、音频时长和总体耗时分别设限。批次工具内部每个模型请求都计量，不能用一次工具调用掩盖几十次付费请求。批量开始前展示规模和资源上限，用户可以取消；已经发出的请求可能完成并产生费用。

首版不绑定特定转录供应商。实施前先验证时间戳、说话人处理、文件限制、数据处理条件和价格；若缺少可靠说话人分离，可先提供转录文本加人工归属界面。转录失败可改为提交文本，不伪造录音内容。

## 7. 页面结构

首页展示两个清晰入口，不要求用户先理解 Agent 技术。

- **个性化分析**：角色库 → 添加角色/上传资料 → 转录与画像核对 → 选择旅行情境 → 输入方案 → 需求匹配 → 对话修改。
- **通用分析**：输入方案 → 目标人群与约束 → 原型覆盖设置 → 批量矩阵 → 对话取舍 → 版本对照。
- **共享工作区**：任务进度、工具操作摘要、证据侧栏、费用/用量、历史报告、方案版本和导出。

角色卡明确显示规则原型、自定义原型或资料角色；资料角色显示画像版本、来源状态和未知项。录音点击引用定位播放片段，文本定位原始消息。低质量转录片段提示用户核对，不显示没有校准依据的精确“画像置信分”。

## 8. 现有项目的复用与改动

| 现有模块 | 处理方式 |
| --- | --- |
| 真人档案、来源与独立情境 | 复用现有事实层，扩展资料解析与画像草稿，不破坏已有来源约束 |
| 规则角色及旅游 JTBD 维度 | 读取并评估后重建显式原型库入口；旧生成接口继续停用，新建原型 API 标明假设性质 |
| 当前固定预测功能 | 保留为意向验证能力；新增需求匹配分析，允许探索性多版本迭代，不将其混入最终测试成绩 |
| 本人反馈与评测分组 | 保留；已揭示答案不能进入待评估预测上下文 |
| 页面导航 | 改为两个主入口，来源、角色库、验证、归档成为辅助导航 |
| 旧资料与展示产物 | 保留在原位置或只读归档；本次不覆盖用户文件 |

建议新增模型：`ProfileDraft`、`ProfileRevision`、`Archetype`、`MediaAsset`、`TranscriptSegment`、`PlanRevision`、`NeedAssessment`、`AnalysisRun`、`CohortSnapshot`、`ComparisonReport`。

关键字段包含角色类型、对象及说话人 ID、情境、事实/推断分类、文本位置/音频时间戳、资料与方案版本、需求状态、硬约束、原型权重来源、批次状态与实际用量。原型库和研究档案分别存储，禁止将原型导入真人台账。

建议增加 `/api/profiles`、`/api/media`、`/api/archetypes`、`/api/analyses` 和 `/api/plan-comparisons` 服务接口，复用 V1 的运行状态、事件、回答、取消和导出机制。上述均为计划接口，不表示现在可用。

原始音频和私有聊天记录不提交 Git。方案分析读取冻结的画像与方案版本；用户更正资料形成新版本，旧结果提示版本已变化。删除资料时处理原始文件、转录、派生画像和缓存，已生成报告按保留政策删除或标记来源已不可访问。首版本机使用；公开部署需要任务和文件的访问隔离。

## 9. 评测与验收

在现有回归之外，建立至少 36 个隔离任务，分为个性化、通用覆盖、迭代/故障三组，每组至少 12 个；开发与最终测试集分开。人物与录音夹具明确标记为测试资料，不写入正式研究台账。

| 类别 | 必测行为 |
| --- | --- |
| 聊天与录音 | 发言者不混淆；时间戳/文本引用可定位；转录低质量和失败有明确状态 |
| 画像 | 事实必须有来源；推断独立标记；未知保持未知；跨对象资料不能自动合并 |
| 需求匹配 | 使用方案原文；区分满足/部分满足/冲突/未覆盖/无法判断；硬约束不能被软偏好平均抵消 |
| 原型覆盖 | 类型隔离、去重、无效组合拒绝；批次失败与未知保留在分母；权重来源可查看 |
| 方案取舍 | 同一案例集合、权重和判定标准下比较；受损群体可见；违反成本上限的候选被拒绝或单独标明不可行 |
| 运行可靠性 | 重复提交幂等、取消、超时、重启、批次恢复及成本上限有效 |
| 注入与资料处理 | 材料中的指令不执行；文件类型/大小校验；删除与访问隔离可验证 |

工程验收要求隔离测试中不存在被接受的越界引用、把推断当事实或将原型覆盖冒充真实人口比例的输出；完整任务成功率初始目标 80%，并公布失败明细。语义质量另由人工评审，不能只检查格式。音频转录质量、画像修订率、需求判断一致性、方案修改接受率、耗时和成本均需实测。

“用户满意”“满足多数真实游客”以及预订转化需另做真实用户验证，不能从原型矩阵或模型自评直接推出。

## 10. 分阶段交付与预计投入

V1 的 12–18 个工作日估算仅适用于较窄的文本研究链路。按本次新增的录音、画像和批量取舍功能，单人借助 AI 编程工具的粗略估算调整为 19–28 个工作日，不含真实用户招募及公开部署；实际以服务验证和现有代码适配结果为准。

| 阶段 | 估算 | 可评审交付 |
| --- | --- | --- |
| P0 需求与数据结构 | 2 天 | 两入口页面流程、角色类型、满足状态、原型维度、报告示例 |
| P1 个性化文本闭环 | 4–6 天 | 添加角色、聊天解析、画像核对、选角色与方案分析、版本保存 |
| P2 通用分析闭环 | 4–6 天 | 多原型选取、批量矩阵、去重、未知与失败计数 |
| P3 Agent 对话迭代 | 3–4 天 | 按结果选工具、缺口追问、约束下候选方案与同集合对照 |
| P4 录音链路 | 3–5 天 | 上传、转录、说话人核对、时间戳引用及删除 |
| P5 验证与演示 | 3–5 天 | 36 个任务、全量回归、成本记录及两个五分钟演示 |

先完成文本链路，再接入录音；两条分析链路共用角色、方案版本和需求判断结构。每阶段更新相关测试，验证通过后创建对应 Git commit。当前版本的保存标签 `pre-agent-upgrade-20261103` 继续作为回滚入口。
