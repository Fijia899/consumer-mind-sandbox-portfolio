## 1. 产品决策

将现有消费者沙盘升级为“面向旅游产品经理的消费者研究 Agent”。研究对象固定为旅游意向人群，产品使用者为旅游产品经理、运营和研究人员。

核心任务：用户提交旅游方案与研究问题，Agent 在获准使用的资料中选择相关旅行情境，查找支持和反向证据，识别信息缺口，交付可追溯的研究简报与下一步验证问题。

用户价值假设：减少研究人员手动找资料、核对引用、整理方案风险的时间，同时保留必要的人工审核。该价值需要通过与手工研究的对照实验验证。

求职展示目标：在已有产品基础上证明工具调用、上下文选择、运行状态管理、错误恢复与评测设计能力。完成代码和演示只能证明系统能力，不能自动证明商业需求或预测效果。

## 4. V1 范围与交付物

首版只完成一类任务：基于已有且获准使用的资料，检查旅游方案与研究对象需求的匹配关系，提出可验证的修改建议。支持单个情境深入分析，以及多个独立情境的逐项对照；跨人分析始终保留每项发现的归属，不输出总体购买比例。

研究简报固定包含：研究问题与范围、使用的资料版本、需求与方案对应、支持证据、反向证据、信息缺口、修改建议、后续访谈问题、限制和运行记录。

V1 暂不建设公开平台自动采集、自动联系受访者、问卷发布、自动预订、付费交易、多 Agent 协作和通用 Harness 平台。资料录入继续复用现有入口。首版不新增模型训练，也不以框架数量作为验收标准。

## 5. 核心交互与演示场景

入口示例（用于演示任务，不作为真实研究事实）：

> 检查这份周末亲子游方案：已有资料中有哪些支持和阻碍进一步了解的因素？列出最需要向本人确认的三个问题，并提出有依据的方案修改建议。

1. 用户输入研究问题和方案，限定资料范围；系统展示预计资源上限。
2. Agent 识别目标与交付物；范围不清且会影响判断时向用户追问。
3. Agent 调用检索、情境读取和证据工具，逐步构建分析。
4. 发现过期情境、矛盾或缺失时，选择补查、追问或保留未知；没有足够资料时交付信息缺口结果。
5. 工作区显示结论及可点击来源，用户可以逐条查看事实、研究分析和方案原文。
6. 用户修改方案后创建新任务版本，展示结论变化及对应依据；不得改写已冻结预测或复用最终测试答案。
7. 导出 Markdown 研究简报。本人反馈继续通过原有流程登记，不由 Agent 生成。

工作台采用三栏：左侧为研究任务和资料范围，中间为工具操作记录与追问，右侧为证据和研究简报。记录展示工具名称、参数摘要、结果摘要、耗时和错误；不展示模型内部思维链。缺口、失败和停止原因应在结果附近可见。

## 6. Agent 执行设计

采用单 Agent、受控工具注册表和服务端状态机。每轮由模型根据任务和已返回的工具结果选择下一项允许的操作；服务端检查参数与权限、执行工具、回传结果，直至提交简报、等待用户回答或达到停止条件。固定的校验与授权规则由代码执行。

建议首版工具：

| 工具 | 输入与输出 | 约束 |
| --- | --- | --- |
| `search_participants` | 研究问题与筛选条件 → 候选档案 ID 及匹配片段 | 只在用户选择的可用范围内检索；返回匹配依据 |
| `get_episode` | 档案 ID、情境 ID → 已核查情境、事实、未知项与日期 | 读取时再次检查归属、状态和有效性 |
| `get_evidence` | 任务内事实 ID → 原始表示、来源、定位及资料版本 | 短引文和已核查摘要保持原表示，不能升级成完整原文 |
| `validate_claims` | 结构化结论与引用 → 有效项、错误项和缺失项 | 结构/归属/逐字校验由代码完成；语义支持关系另需审核 |
| `ask_user` | 缺失字段与问题 → 等待用户作答 | 用户对方案的解释不自动成为受访者自述 |
| `submit_report` | 结构化简报 → 校验通过的报告版本 | 拒绝不存在或越界的引用；每条建议绑定依据或标明待验证假设 |

首版研究任务不自动创建预测。需要三组意向预测时，由用户在现有预测入口确认具体人物、情境、方案、预测范围和分组后执行。后续如将预测包装成工具，也必须沿用这些输入及冻结规则，不能通过报告重试绕过最终测试限制。

上下文按任务组织：保存完整任务事件；传给模型的内容只含必要的情境、事实 ID、明确标注的分析及工具结果摘要。当前计划与历史资料分别呈现；本人反馈和最终测试答案不进入待评估预测上下文。模型不得直接访问生产 JSON 文件或执行任意代码。

## 7. 状态、错误恢复与成本

任务状态：`queued → running → waiting_user / completed / insufficient / failed / cancelled / interrupted`。用户回答后从持久化的等待点继续；服务重启将未完成的运行标记为 interrupted，首版不自动重放有副作用的步骤。手动继续时创建关联的新尝试并复查资料版本。

暂定每次任务最多 12 次工具调用、180 秒总时长、18,000 累计模型输入输出 token；这些是初始保护值，试运行后调整。累计用量以供应商返回为准，缺失时标为未知并采用保守估算，不显示为零。单次模型请求仍受总任务截止时间约束，沿用底层重试时必须避免叠加多层重试。

网络临时故障允许只读工具在剩余预算内重试一次；参数或引用校验失败将错误返回 Agent 修正，最多两轮；权限错误、取消和预算耗尽立即停止。首版断连后可重新打开任务查看已持久化事件；取消采用协作式停止，正在进行的远端请求可能完成并计费，但停止后不得继续调用或提交结果。

每项工具操作记录 run ID、attempt ID、序号、参数摘要、结果摘要、资料版本、开始结束时间和错误码。任务启动使用幂等键，重复提交返回原任务。Trace 和报告导出均避免暴露密钥、无关个人信息及完整非公开原文。

## 8. 后端、数据与 API 改动建议

继续使用 FastAPI 和现有页面技术，先复用服务层，不要求更换前端框架。

建议新增文件（均为计划路径，本次未创建）：

- `backend/agent_schemas.py`：任务、事件、工具输入输出和研究简报结构。
- `backend/services/research_agent.py`：模型工具循环、停止条件和预算检查。
- `backend/services/agent_tools.py`：受控工具与现有档案服务适配。
- `backend/services/agent_store.py`：SQLite 任务、尝试、事件和报告持久化。
- `backend/routes/agent.py`：任务启动、查看、回答、取消与导出。
- `frontend/agent.html`、`frontend/js/agent.js`：研究工作台。

新增 SQLite 只保存 Agent 任务状态；现有研究台账保留原存储方式和单进程约束。SQLite 与 JSON 不存在跨库事务，因此首版工具仅读取台账，报告保留资料版本及输入快照；再次读取时发现版本变化必须标识，不能静默混用。私有运行数据库、临时文件和报告默认加入 Git 忽略。

建议 API：

| API | 行为 |
| --- | --- |
| `POST /api/agent/runs` | 以幂等键创建任务并返回 ID，后台执行 |
| `GET /api/agent/runs/{id}` | 查询状态、范围、用量和报告 |
| `GET /api/agent/runs/{id}/events?after=cursor` | 增量获取可恢复的事件；首版使用轮询 |
| `POST /api/agent/runs/{id}/answers` | 对指定等待点作答，禁止重复恢复同一等待点 |
| `POST /api/agent/runs/{id}/cancel` | 请求停止，重复取消保持幂等 |
| `GET /api/agent/runs/{id}/report` | 导出经校验的 Markdown 简报 |

首版默认本机运行。公开可访问版本在部署前还需补齐访问控制、用户间数据隔离和资源限额；演示可先采用本机现场运行与经过脱敏的预录回放，并明确区分实时执行和回放。

## 9. 评测与验收

评测分开回答“Agent 是否完成研究任务”和“意向判断是否符合本人反馈”。不得用引用格式正确或程序测试通过来证明语义结论正确。

首版建立至少 24 个隔离评测任务：正常分析、反向证据/冲突、资料不足/过期、跨人物或情境引用、工具故障/取消/重启、资料中混入指令各 4 个。评测资料使用获准资料的脱敏副本或明确标注的隔离夹具，不写入生产台账。预期依据和可接受缺口由人工先审核，开发集与最终测试集分别管理。

| 指标 | 定义与暂定验收线 |
| --- | --- |
| 引用结构和归属 | 所有已交付报告引用均可解析且在任务范围内；隔离集越界接受数为 0 |
| 语义依据 | 人工核查结论是否由所引资料支持，逐项报告结果，不只看模型自评 |
| 正常任务成功率 | 在预先定义交付要求下至少 80%；公布任务数与失败原因 |
| 缺口处理 | 缺失事实不被补造；不足案例的关键缺口均在结果中出现 |
| 失败处理 | 故障、取消、预算耗尽和重启案例均有明确终态及事件，不显示假成功 |
| 时间与成本 | 报告真实耗时、调用数、token 与未知用量；根据试运行设定性能目标 |
| 用户研究效率 | 用相同任务比较人工流程与 Agent 辅助流程的耗时、纠错次数和结果可用性 |

80% 是首版工程验收目标，不是已有成绩或真实预测准确率。24 个任务用于起步验收，不能证明广泛泛化能力；最终报告应同时说明独立资料/参与者数量与类别覆盖。

三组意向预测继续用同一人的后续反馈比较覆盖率、证据不足率、命中率、Macro F1 和混淆表，沿用开发/最终测试分组与答案揭示规则。报告辅助价值可以先验证，真实预测效果需另行招募与收集反馈。

## 10. 分阶段实施与提交

按单人借助 AI 编程工具估算 12–18 个工作日，不含招募本人反馈、公开部署和大规模用户验证；每阶段完成后更新相关测试、通过验证并单独提交 Git。

| 阶段 | 时间估算 | 交付与退出标准 |
| --- | --- | --- |
| P0 基线保存与方案评审 | 本次完成 | 文件备份、升级前标签、方案与验证记录 |
| P1 运行底座 | 2–3 天 | 状态机、持久化、幂等、事件、预算；取消及中断测试通过 |
| P2 工具与执行循环 | 3–4 天 | 真实模型按结果选择工具；正常、缺口、错误修正任务跑通 |
| P3 工作台与研究简报 | 3–4 天 | 追问、引用查看、恢复查看、方案版本和导出可用 |
| P4 评测与加固 | 3–5 天 | 至少 24 个任务、人工核查、故障回归与成本记录 |
| P5 演示包装 | 1–2 天 | 五分钟演示、回放说明、架构图、评测报告与项目描述 |

完成 P2 时复查 Agent 相比固定工作流的价值：若多数任务始终走同一路径且没有质量或效率收益，应缩减动态决策范围，保留适合的固定校验流程。

## 11. 交付展示标准

展示材料包含一个正常案例、一个资料不足案例、一个工具失败案例；能够从结论回到来源，并回放真实工具事件。任务执行成功与研究结论正确分别解释。

完成后可使用的项目描述模板：
